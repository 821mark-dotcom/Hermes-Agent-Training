Conductor — Mission Control

⏱ 15 minIntermediateAdvanced
ELI10

Conductor is your mission orchestrator. You describe a goal in plain English. It breaks the mission into subtasks and assigns them to a pool of worker agents, which may appear as names like Nova, Pixel, or Blaze. Those names are example roster labels for the mission team, not special pre-created personas you must build manually. Conductor coordinates the work and shows progress as each slice completes.

🖥️ Hermes Workspace — Conductor page
  • New Mission — describe your goal; Conductor decomposes it
  • Agent team — names such as Nova, Pixel, Blaze are mission-worker labels shown with status: Ready / Working / Done
  • Mission list — all active and past missions with live status
  • How it works — button explains the orchestration model
  • Live updates — agents report progress checkpoints in real time
ℹ️ Note on Conductor availability

Conductor uses the dashboard mission API when hermes dashboard is running. When the dashboard endpoint is absent, Workspace falls back to native Swarm dispatch. Both paths produce the same result.

Use Case — Build a New API Endpoint, Start to Finish

Goal: Add a /api/reports/weekly endpoint that queries Jira, formats data, and returns JSON. You want: the implementation, tests, and updated README — without touching the keyboard yourself.

Learning / Building Path
Use Conductor after Tasks: Conductor is the next level up from the board. It takes a goal and decomposes it into tasks automatically. This is the right place to move after you understand the board lifecycle.

Sequence: Tasks → Conductor → Operations → Swarm. Beginner combo: one small mission, clear success criteria, and one Builder-type task. Intermediate: multi-agent mission with tests/docs. Advanced: parallel workstreams, custom profiles, and swarm automation.

Live Setup — Step by Step

  1. Ensure hermes gateway run and hermes dashboard are both running
  2. Open Hermes Workspace → navigate to Conductor
  3. Click New Mission — describe your goal (see prompt below)
  4. Conductor decomposes the mission: Builder agent gets the code task, Reviewer gets tests, Scribe gets docs
  5. Watch the worker labels (for example Nova/Pixel/Blaze) change from Ready → Working
  6. Checkpoints appear as agents report progress — review without blocking them
  7. Mission completes: review the output in the mission results panel

⚡Too vague? It pauses, it does not silently execute: If a mission is underspecified — for example, no target files, no success criteria, no constraints, or no clear scope — Conductor should stop and ask for the missing details instead of guessing. In practice, the mission stays in a Blocked / Needs clarification state until the goal is actionable; it does not start running in the background or rely on a blinking-only signal. Once the missing detail is supplied, Conductor can decompose the work and dispatch the agents.
⚡Write the mission like a ticket: Include requirements, constraints, and success criteria. The more specific you are, the better Conductor decomposes the work.
⚡git commit before launching: Conductor makes real file edits. A clean commit before a mission = easy rollback with git stash if needed.
⚡Checkpoints are milestone updates: Each agent emits a checkpoint in the Conductor mission panel as it completes a slice of work. They show who reported it (for example, a worker labeled Nova or Blaze), what was finished, and optionally a short summary of the result or next step. These labels are just the mission roster names; they are not separate app accounts you had to create ahead of time. You can review them live in the mission log / live status view — they are your early-warning signal for drift, errors, or a task that needs attention before the whole mission completes.
⚡Human planning / vetting gate is possible: Yes — if you want Conductor to pause for a human plan review, include that explicitly in the mission prompt. Example: Stop after the implementation plan is written and wait for human approval before any code changes begin. In that pattern, Conductor creates a planning or review task first, and the mission does not advance to the execution work until the human approves or adds a comment. This is not an automatic hidden toggle; it is enforced by the mission design and the task dependency graph.

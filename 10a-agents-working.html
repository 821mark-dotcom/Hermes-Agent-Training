🖥️ Layer 3 · Hermes Workspace

Agents Working — From One Prompt to a Coordinated Mission

⏱ 8 minBeginnerIntermediateAdvanced
ELI10

Hermes is useful as a single chat assistant, then as a task planner, then as a coordinated team. The right mode depends on the job. For a quick answer, use one chat. For a real project, break the goal into tasks and assign them. For repeated or multi-step work, run the mission through Conductor or Swarm.

Learning / Building Path
The progression is simple: single agent → structured tasks → orchestrated work. If the goal is narrow and clear, one prompt is enough. If the scope is larger, first decompose it into tasks. If it is a recurring or multi-step effort, use Conductor, Operations, or Swarm.
Use Case 1 — Single-agent work

When to use it: the job is small, specific, and easy to validate. Example: investigate a failing test, explain a config file, or draft a short update.

Use Case 2 — Task-based work

When to use it: the goal has multiple moving parts but still needs a human in the loop. Example: create a sprint report, update docs, validate edits, and review output before shipping.

Use Case 3 — Coordinated multi-agent work

When to use it: the job is larger than a single pass: building a feature, writing docs, testing changes, and preparing a summary for review. This is where Conductor, Operations, and Swarm become useful.

ELI10: Conductor vs. Operations vs. Swarm

Three different ways to get agents working, from most-automated to most-manual:

How they relate
  • Conductor = "tell it the goal, it plans the graph for you." You type a plain-English mission; Conductor decides how to break it into tasks and who does what. It has no separate engine of its own — it either calls the Dashboard's mission API (if hermes dashboard is running) or falls back to the same Swarm graph-creation mechanism as hermes kanban swarm. Conductor is a planner sitting on top of Swarm, not a separate system.
  • Swarm = the actual engine room. hermes kanban swarm creates the real task graph (parent/child cards: workers → verifier → synthesizer), and tmux-backed worker processes are supposed to auto-pick-up tasks from that graph. This is what Conductor calls internally when you don't specify the graph yourself.
  • Operations = the manual, no-automation path. You launch each agent yourself, one at a time, and you are the relay — copying one agent's output into the next agent's prompt. It never touches Conductor or Swarm at all.
Call this directly when...Why
ConductorYou have a real goal but don't want to plan the task breakdown yourself — best default entry point for a fresh idea.
Swarm (hermes kanban swarm CLI)You already know the exact decomposition you want and need deterministic, scriptable control — e.g. for repeatable automation.
OperationsSwarm/Conductor is broken or unavailable, you want full manual visibility/control over each step, or the job is small enough that being the relay yourself gives the clearest audit trail.

Interacting with agents directly, beyond Conductor

Conductor is the friendliest front door, but it is not the only — or even the required — way to work with agents.

  • You can always drop down a level and talk to an individual agent directly, whether that's an Operations profile session or a single worker's tmux pane. Nothing requires going through Conductor's plain-English mission layer if you already know exactly which agent you want and what you want it to do.
  • This is not a workaround or a "lesser" path — it is more transparent (you see exactly what each agent said/received), more debuggable (you can isolate exactly which agent is misbehaving), and fully unaffected by bugs in the orchestration layer above it.
  • Trade-off: going direct means you become the router/relay between agents — there is no automatic handoff, so you're responsible for passing context from one agent to the next. Manageable for a small number of agents (2-4); does not scale well to dozens, which is where Conductor/Swarm's automatic dispatch earns its keep.
  • Rule of thumb: start with Conductor for a new, not-yet-understood goal; drop to direct agent-by-agent interaction in Operations when Conductor/Swarm is unavailable, misbehaving, or when you specifically want the transparency of being the relay yourself.
Just Show Me — Three Successive Hermes Workflows
You — one agent, one job
Do this
Use one focused prompt for a short, bounded task.
Paste into chat
Review the current repo and tell me which file is the best place to start if I want to understand the app entry point and how it initializes. Keep it brief and point me to the exact file names.
Expected Result: Hermes gives a concise, repo-specific answer pointing to the most relevant file or entry point for the current project.
You — break the task down
Do this
Use a structured prompt when the work has multiple steps and approvals.
Paste into chat
I need to improve this project. Break the goal into 5 concrete tasks with clear owners and dependencies. Put the output into a Kanban-ready list with status labels: Ready, In Progress, Review, Done. Include: what to inspect, what to change, and how to validate each one.
Expected Result: The output is a structured five-step list of tasks with dependencies and status labels suitable for a board or sprint workflow.
You — orchestrated mission
Do this
Use Conductor or Operations when a job needs parallel work, multiple roles, and checkpointing.
Paste into chat
Run a mission to upgrade the project with a small but real improvement: add one meaningful feature, update docs, run validation, and summarize the result. Break the work into parallel streams: builder, reviewer, and docs. Checkpoint after each stage and stop if a task becomes ambiguous or a blocker is found.
Expected Result: The orchestration prompt creates a multi-role mission or plan that separates work into single-agent, task-based, and coordinated stages as described.
🧭 When to move up a level
  • Stay at one-agent mode when the goal is narrow and you want quick feedback.
  • Move to task mode when the effort needs sequencing, review, or tracking across multiple edits.
  • Move to orchestration when the work is large, multi-step, and benefits from parallelism, checkpoints, or worker roles.
⚡Don’t over-orchestrate: if the job fits in one pass, don’t create a mission. The simplest tool is the fastest path.
⚡Ambiguity is a real signal: if a task is vague, Hermes should slow down and ask for clarification instead of proceeding with a wrong assumption.
⚡Use the board for visibility: when work is multi-step, the Kanban board makes dependencies and handoffs far easier to reason about.

Vibe Coder Case Study — Verified 4-Agent Sequential Pipeline

⏱ 20 minIntermediate
ELI10

This is a real, verified run — not a hypothetical. A vibe coder wanted to prove they could use multi-agent orchestration and walk away with a finished result. We ran a 4-agent sequential pipeline through Operations: a Researcher compares options, a Writer turns that into a recommendation + code, a Vetter actually checks the code runs and catches a real bug, and an Orchestrator reports the final status back in plain English. Every step below actually happened, including the mistakes.

🖥️ What ran, in order
  • Researcher (Sage) — compared plotly/bokeh/altair for financial dashboards, 13 cited sources
  • Writer/Synthesizer (Scribe) — turned raw research into a recommendation + Python code stub
  • Vetter/Approver (Ops, repurposed) — actually executed the code, caught a real data bug, returned NEEDS REVISION
  • Main Orchestrator — synthesized the full chain into a 3-sentence human-readable status + next action
Hermes Workspace · Operations · each agent is a separate session; the facilitator relays one agent's output into the next agent's task prompt — that relay is the handoff
Why sequential, not parallel

Real-world multi-agent orchestration does not require concurrency. The defining feature is distinct agent identities + a real handoff of output/context between them — sequential handoff (researcher → writer → reviewer) is a legitimate, common pattern, not a lesser version of "real" orchestration. What disqualifies a run is a single agent doing every step itself in one session, no matter how many tool calls it makes internally.

Where to vet handoffs and output (by design)

  • Operations → individual agent's Chat/session view — the detailed audit trail per agent: every tool call, reasoning step, and the exact task prompt it received, including handoff content pasted in from the previous agent.
  • Operations → Outputs tab — a consolidated summary across all running agents for a quick check without opening each transcript.
  • Because this pipeline used manual relay (not automated Swarm/Conductor handoff), the "chatter" between agents is not automatic — it is each agent's last message pasted as the next agent's first message. To audit the full chain, open each of the 4 agents' Chat sessions in sequence.

⚡Fix bad defaults once, permanently — not per task: the first fix to Sage/Ops was a task-specific system-prompt rewrite (all about charting libraries), which turned out to save permanently to ~/.hermes/profiles/<name>/config.yaml — meaning every future session would stay stuck on that one topic. Corrected properly: rewrote both profiles to be genuinely generic and reusable (a general-purpose research agent, a general-purpose QA/vetter agent). Task-specific asks belong in the per-session message, not the permanent profile.
⚡Clarify only upfront, never mid-flight: an early draft of Sage's generic prompt said "ask a clarifying question if the task is ambiguous." That's wrong for a walk-away pipeline — a mid-flight question has nowhere to go if no one's watching, and stalls everything. This project's own Conductor documentation (Section 07) confirms the correct pattern: Conductor pauses and asks before a mission starts if it's underspecified, but once dispatched, agents should default to a clearly-labeled reasonable assumption and keep going — only surfacing genuine blockers (missing access, destructive/irreversible action, direct contradiction) as a note in the final output, never a pause-and-wait.

Confirmed bug + fix — zsh crashes Swarm workers

Before falling back to Operations, we first tried hermes kanban swarm. The task graph was created correctly every time, but the tmux-backed worker launcher (hermes-workspace/src/routes/api/swarm-dispatch.ts, buildHermesTmuxLaunchCommand) captured exit codes with status=$? — status is a read-only reserved variable in zsh (macOS/most Linux default shell), so every worker crashed on launch, unconditionally, before doing any real work.

Verified directly: zsh -c 'status=$?' reproduces zsh: read-only variable: status on demand. Confirmed not a network/corporate-proxy issue (npm registry reachable, HTTP 200). Fixed and verified: renamed the variable to exit_code.

ℹ️ This bug never affected the pipeline above

The zsh bug only lives in the Swarm/tmux code path. A vibe coder on a brand-new machine, with no fix applied, can still run the entire Researcher → Writer → Vetter → Orchestrator pipeline above successfully — the fix is only needed for Swarm mode specifically.

Live Setup — Step by Step

  1. Ensure hermes gateway run and the Workspace UI are both running (Phase 0 check)
  2. Open Hermes Workspace → Operations → New Agent → select a preset, then rewrite its description + system prompt to be generic and reusable (fix once, not per task)
  3. Send the Researcher agent the task; wait for it to finish
  4. Copy the Researcher's final output into a new agent's (Writer) task message
  5. Copy the Writer's final output into a new agent's (Vetter) task message, asking for a clear verdict
  6. Send the Main Orchestrator (pre-existing) a short status summary referencing all 3 agents' results
  7. Review each agent's individual Chat session to audit the full handoff chain
⚡Expect at least one "operation interrupted": in this live run, both the Researcher and the Vetter got cut off mid-response at least once. A simple "please continue" follow-up message resolved it every time — treat this as a normal recovery step, not a fatal error.
⚡The vetting gate caught a real bug: the Vetter executed the handed-off code and found a genuine data bug (introduced during the human relay, not by the Writer). This is exactly the value a vetting step is supposed to add — treat any "NEEDS REVISION" verdict as the pipeline working correctly, not failing.
⚡Bar for a legitimate "I did multi-agent orchestration" claim: at least 2 distinct agents with a real handoff of output/context between them. Concurrency is not required.

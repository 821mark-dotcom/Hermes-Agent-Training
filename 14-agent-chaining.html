Agent Chaining & Handoffs

⏱ 12 minIntermediateAdvanced
ELI10

When one AI agent finishes a job, how does the next agent know what was done and what to do next? In Hermes, there are two ways: a quick direct hand-off (like passing a note) and a durable work queue (like a shared whiteboard where anyone can read the history). The whiteboard version is more powerful — it survives crashes, allows human check-ins, and is the foundation for Conductor, Swarm, and Operations.

Two Chaining Mechanisms

Hermes has two distinct ways agents can chain work. They look similar but behave very differently:

⚡ delegate_task 🖥️ Kanban Parent Link
ShapeRPC call — fork → joinDurable message queue + state machine
Context handoffParent must pass everything explicitly in goal/contextParent's summary+metadata auto-flows to child via kanban_show()
DurabilityProcess-tied — restart = lostSQLite-backed — survives restarts, crashes
Human in loopNot supportedBlock → comment → unblock at any point
Agent identityAnonymous subagentNamed profile with persistent memory
Best forQuick single-turn sub-tasks within a sessionMulti-agent pipelines, overnight sprints, anything needing audit trail

One-sentence rule: use delegate_task when you need a fast answer back in the same conversation. Use Kanban when work crosses agent boundaries or might need human input.

How the Kanban Handoff Actually Works

This is the exact mechanism. There is no magic — it is three steps:

⚡ Hermes Agent — The Three-Step Handoff

Step 1 — Agent X completes with a structured handoff:

Agent X (tool call before exiting)
kanban_complete( summary="Researched AI funding landscape. Key finding: seed rounds up 40% YoY. Full notes in research.md", metadata={"changed_files": ["research.md"], "decisions": ["focus on Series A", "exclude EU for now"]} )

Step 2 — Y's task was created with X as a parent:

You (CLI or Dashboard)
Do this
Use this prompt in the appropriate chat, terminal, or field.
Paste into chat
hermes kanban create "Write launch post from research findings" \ --assignee writer \ --parent t_x1a2b3 # X's task id — Y waits here until X is done

Step 3 — When Y spawns and calls kanban_show(), it receives:

What Agent Y sees in its context
Do this
Use this prompt in the appropriate chat, terminal, or field.
Paste into chat
## Parent task results ### t_x1a2b3 (completed 4 minutes ago) Researched AI funding landscape. Key finding: seed rounds up 40% YoY. Full notes in research.md _metadata_: {"changed_files": ["research.md"], "decisions": ["focus on Series A", "exclude EU for now"]}

Agent Y did not need any special configuration. The board wires the context automatically. Y's task sat in todo status while X ran, then auto-promoted to ready the moment X completed. The dispatcher picked it up on the next 60s tick.

Profile Routing — How the Decomposer Chooses Assignees

When you drop a task in Triage with auto-decompose on, the decomposer reads your installed profiles and their descriptions to decide who gets what child task. Without descriptions, it can only route by name.

Set description via CLI

Terminal
hermes profile describe researcher \ --text "Searches sources, synthesizes findings into structured notes with citations"

Set description via Dashboard Kanban

Dashboard → Kanban tab → ▸ Orchestration settings → per-profile description editor. Click a profile name, type the description, save. Same result as the CLI command.

What's Already Running Out of the Box

✅ Dispatcher

Runs inside the gateway. dispatch_in_gateway: true is the default. 60s tick. No setup needed.

✅ Auto-decompose

auto_decompose: true is the default. Drop a task in Triage → decomposer fans it out automatically.

✅ KANBAN_GUIDANCE

The worker lifecycle instructions are auto-injected into every spawned worker. No per-profile skill setup required.

Three Canonical Chaining Patterns

P1 · Fan-out

N agents run the same role in parallel. Each gets an independent task. No parent links needed.

researcher-a → t_r1
researcher-b → t_r2
(run concurrently)

P2 · Pipeline

Sequential chain: A finishes → B starts with A's output → C starts with B's output.

researcher → writer
[--parent t_r1]
reviewer [--parent t_w1]

Swarm v1 Topology

Parallel workers → single verifier → single synthesizer. Atomic graph creation in one command.

hermes kanban swarm "goal"
--worker researcher:task
--verifier reviewer
--synthesizer writer
P2 Pipeline — full CLI example
# Step 1: create the research task hermes kanban create "Research AI funding trends 2026" --assignee researcher # Step 2: create the writing task — linked to step 1 # (t_r1 is the id returned by step 1) hermes kanban create "Write a 300-word launch post from research findings" \ --assignee writer \ --parent t_r1 # Step 3: create a review task — linked to step 2 hermes kanban create "Review launch post for accuracy and tone" \ --assignee reviewer \ --parent t_w1 # Watch the board live hermes kanban watch
🖥️ What Conductor and Swarm UI do under the hood: They both use this Kanban parent-link pipeline internally. Conductor decomposes your mission into child tasks with parent links and assignees. Swarm routes to pre-defined worker → verifier → synthesizer roles. The Workspace UI is a front door; the actual wiring is always the Kanban board you can inspect at localhost:9119/kanban.
⚡The quality of summary= is the quality of the handoff. A vague summary="done" leaves the next agent with nothing to go on. A good summary names what changed, what was decided, and what the next agent should know. The metadata dict is machine-readable — the next agent can use it to find files without parsing prose.
⚡Inspect any worker's context before it runs: hermes kanban context <task_id> shows exactly what the spawned worker will see — title, body, parent results, comments, prior attempts. Use this to debug handoff quality.
⚡Orchestrator profiles should not execute. If you create an orchestrator profile, restrict its toolsets to kanban, gateway, and memory only. This prevents the orchestrator from accidentally doing implementation work instead of routing it.
⚡auto_decompose vs manual: Keep auto_decompose: true (the default). If you want to control exactly what gets decomposed, use the ⚗ Decompose button on individual triage cards in the Dashboard Kanban instead of toggling auto off globally.
